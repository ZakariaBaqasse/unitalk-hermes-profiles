# Equinet A1 Twenty Company Staging

Use immediately after a compact `a1.discovery-result.v1` result is persisted. This is the mandatory post-discovery path.

## Scope

- One Twenty Company per named returned lead.
- One human-review queue; no website/no-site split.
- No Person records.
- Website, evidence, score and confidence are optional for storage.
- New Companies start as `DISCOVERED`.
- Restaging must preserve existing `DISCOVERED`, `HELD`, `ELIGIBLE` or `REJECTED` reviewer status.
- Never create Opportunities, Tasks, messages, campaigns or outreach.

## Deterministic helper

Use PATH-selected `python3`; do not invoke an absolute interpreter path from cron.

### 1. Prepare the batch

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py prepare-batch \
  --input <discovery-result.json> --output <batch.json>
```

Every input fingerprint becomes either:

- `ready` with a Company payload and lookup plan; or
- `blocked_missing_company_name` with no invented identity.

### 2. Preflight and decide

For each ready item, execute the emitted `find_many_companies` lookups through Twenty MCP. Save raw responses and run `normalize-find` so matching always uses normalized `result.records`. Supply arrays named `fingerprint_matches`, `domain_matches`, and `possible_matches` to:

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py decide \
  --plan <plan.json> --matches <matches.json> --output <decision.json>
```

Outcomes:

- `create` → execute emitted `create_many_companies` arguments;
- `update` → execute emitted UUID-scoped `update_one_company` arguments;
- `blocked` → write no CRM record and persist `possible_match`.

Never use `update_many_companies` for A1 restaging.

### 3. Write-response handling, read-back and reconcile

Save every raw create/update response before deriving any disposition. In the live Twenty MCP, `create_many_companies` may return a `result` array containing only `{id}` values rather than a single Company record. Do **not** pass that array to `normalize-record`: extract the sole returned Company ID from the saved raw response, then make `find_one_company` with `select: ["*"]`. `normalize-record` applies to that single-record read-back, which is the authoritative verification input.

Before a write, the emitted payload must be schema-valid for the live Twenty API. In particular, the current API rejects formatted US phone strings such as `270-402-4174`; the deterministic staging helper must emit an API-accepted value (normally E.164, for example `+12704024174`) or omit the phone before the write plan is emitted. Do not manually mutate an emitted write payload in a cron run: record a deterministic payload rejection as `sync_failed` and repair/test the helper separately.

After create/update, execute `find_one_company` with `select: ["*"]`, normalize that response with `normalize-record`, then:

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py reconcile \
  --plan <plan.json> --decision <decision.json> \
  --company-id <id> --readback <company.json> --output <reconciliation.json>
```

A lead is `staged` only after verified read-back. Preserve uncertain writes as `sync_failed`; never blindly retry a create whose remote outcome is unknown.

### 4. Finalize the batch

Build a dispositions document with one terminal outcome per input fingerprint, then:

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py finalize-batch \
  --batch <batch.json> --dispositions <dispositions.json> \
  --output <staging-index.json>
```

Allowed dispositions are `staged`, `possible_match`, `sync_failed`, and `blocked_missing_company_name`. The complete staging index is the only valid consumed artifact for the discovery ticket.
