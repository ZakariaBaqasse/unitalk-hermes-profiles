# Equinet n8n Discovery and Twenty Staging Control

Use this skill to start the exposed Equinet n8n discovery orchestrator, retrieve its compact result exactly once, and stage each named returned lead as a Twenty Company for human review.

## Mandatory path

```text

→ durable polling ticket
→ retrieve Build Final Discovery Result once
→ deterministic Company payloads and duplicate preflight
→ Twenty Company create/update and read-back
→ complete staging index
→ human review in Twenty
```

Official-site enrichment, ICP qualification, confidence, scoring, ranked review packages, exports and A2 are not part of this mandatory retrieval path. Run them only as separately requested post-review work.

## Hard boundaries

- Create or update Twenty Companies only. Never create People.
- Stage named leads regardless of website, evidence or score.
- New Companies use `discoveryStatus: DISCOVERED`.

- Never write HubSpot, create Opportunities/Tasks/campaigns/messages, invoke A2 or initiate outreach.
- Never invent a Company name. Missing names end as `blocked_missing_company_name`.

## Discovery request input contract

Supply the main orchestrator through the MCP `webhook` input shape, using a `POST` body. The workflow's live validation node accepts:

```json
{
  "requested_count": 10,
  "segment": "farrier",
  "location": {
    "country": "US",
    "state": "Kentucky",
    "city": "Lexington"
  }
}
```

Accepted fields:

- `requested_count` (preferred) or `target_count`: numeric requested lead count; defaults to `100`, minimum `1`.
- `overfetch_factor`: numeric, defaults to `2`, minimum `1`; n8n derives `discovery_target = ceil(requested_count × overfetch_factor)`.
- `segment`: `farrier` (default) or `horse_owner`; any other value is rejected.
- `location`: object. `location.state` is required; `location.country` or `location.country_code` defaults to `US`; city may be supplied for focus.
- `focus`: optional array.
- `run_id`: optional; n8n generates one if omitted.
- `source_policy_version`: optional; defaults to `approved-source-register-v1`.

Do not invent alternate field names or omit `location.state`. Keep the request within the active runtime candidate limit. The code accepts the body from `$json.body` or `$json`, but MCP runs should use `inputs: { type: "webhook", webhookData: { method: "POST", body: ... } }`.

Use immediately after a compact `a1.discovery-result.v1` result is persisted. This is the mandatory post-discovery path: every named lead must receive exactly one terminal staging disposition before the discovery ticket can be consumed.

## Scope

## Deterministic helper

Use PATH-selected `python3`; do not invoke an absolute interpreter path from cron.

### 1. Prepare the batch

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py prepare-batch \
  --input <discovery-result.json> --output <batch.json>
```

Every input fingerprint becomes either:

- `ready` with a Company payload and lookup plan; or
- `blocked_missing_company_name` with no invented identity.

### 2. Preflight and decide

For each ready item, execute the emitted `find_many_companies` lookups through Twenty MCP. Save raw responses and run `normalize-find` so matching always uses normalized `result.records`. Supply arrays named `fingerprint_matches`, `domain_matches`, and `possible_matches` to:

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py decide \
  --plan <plan.json> --matches <matches.json> --output <decision.json>
```

Outcomes:

- `create` → execute emitted `create_many_companies` arguments;
- `update` → execute emitted UUID-scoped `update_one_company` arguments;
- `blocked` → write no CRM record and persist `possible_match`.

Never use `update_many_companies` for A1 restaging.

### 3. Write-response handling, read-back and reconcile

Save every raw create/update response before deriving any disposition. In the live Twenty MCP, `create_many_companies` may return a `result` array containing only `{id}` values rather than a single Company record. Do **not** pass that array to `normalize-record`: extract the sole returned Company ID from the saved raw response, then make `find_one_company` with `select: ["*"]`. `normalize-record` applies to that single-record read-back, which is the authoritative verification input.

Before a write, validate the **actual emitted plan** against the live Twenty API constraints; do not assume the helper version is already compliant. The helper normalises unambiguous US public phone values to canonical E.164 (for example `270-402-4174` → `+12704024174`) and canonicalises already-plus-prefixed values. It omits masked, extended, ambiguous or non-US non-E.164 values rather than guessing. The original public value remains in the immutable discovery artifact; only the API-safe form may appear in the Twenty write plan. If a prepared plan still contains a formatted phone, do not invoke `create_many_companies`/`update_one_company` and do not manually mutate its payload in a cron run: preserve the plan and decision artifacts, record the terminal disposition as `sync_failed` with a `deterministic_staging_payload_rejected_prewrite` reason, then repair and test the helper separately. This prevents ambiguous remote writes and makes the compatibility regression auditable.

**Masked-phone regression guard.** Treat a value containing masking characters (for example `+140****3078`) as an invalid emitted payload only when that value is confirmed in the raw persisted plan JSON. Chat, `read_file`, MCP, and terminal-rendered output can redact publicly displayed phone values; a rendered masked value is not proof that the payload is masked. Before rejecting any ready item, run this local deterministic raw-file check; it returns aggregate/non-sensitive counts only:

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py validate-batch-phones \
  --batch <batch.json> --output <phone-validation.json>
```

Proceed with duplicate preflight and staging only when its `status` is `valid`. Reject and record `sync_failed` with `deterministic_staging_payload_rejected_prewrite: masked_phone_in_emitted_plan` only if the raw validator reports masking characters or invalid values. Never create a terminal disposition from a redacted display. Retain the plan and validation artifacts and repair/test the helper outside the cron run only for a confirmed raw-payload defect.

After create/update, execute `find_one_company` with `select: ["*"]`, normalize that response with `normalize-record`, then reconcile. Twenty may store a written E.164 US phone as `primaryPhoneNumber` without the country prefix plus a separate `primaryPhoneCallingCode: "+1"`; the helper reconciles their canonical combination against the emitted E.164 value. Treat an unverified read-back mismatch as `sync_failed` and do not retry the create. In particular, record the literal expected and returned values: URL serialization may remove a trailing slash, which must be treated as a reconciliation compatibility issue until the deterministic normalizer is tested and versioned to accept that equivalence.

```text
python3 skills/crm/evidence-aware-crm-staging/scripts/stage_twenty_company.py reconcile \
  --plan <plan.json> --decision <decision.json> \
  --company-id <id> --readback <company.json> --output <reconciliation.json>
```

A lead is `staged` only after verified read-back. Preserve uncertain writes as `sync_failed`; never blindly retry a create whose remote outcome is unknown.

### 4. Finalize the batch
